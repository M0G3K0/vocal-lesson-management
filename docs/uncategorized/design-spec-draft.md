# 設計・仕様案（未確定）

この文書は、これまでの会話で出た設計・仕様・実装方法の候補を、要求書と分けて記録するためのものです。

ここに記載した候補は未確定です。要求書に記載した要求を実現する方法を検討する際の材料として扱います。

採用技術とアプリケーション構成については、[バックエンドのアプリケーションアーキテクチャ](./BACKEND-ARCHITECTURE.md)と[フロントエンドのアプリケーションアーキテクチャ](./FRONTEND-ARCHITECTURE.md)に合意済みの方針を記録しています。

## 1. サービス形態の候補

- スマートフォン向けWebアプリ
- PCからも利用できるレスポンシブなWeb UI
- 必要に応じてPWA化
- Chrome拡張は本体にしない

## 2. システム境界の候補

```text
スマートフォン・PCのWeb UI
        ↓
バックエンド
        ├─ SHEER連携
        ├─ Google Calendar連携
        ├─ 経路検索
        └─ 任意でGmail連携
```

Gmailは予約情報の本体ではなく、予約完了通知などを扱う補助的な連携先とする案が出ています。ただし、Gmailを利用するかどうかは未決定です。

## 3. ドメイン境界の候補

```text
ReservationSource
  ├─ SHEER予約一覧
  ├─ Gmail確認メール
  └─ 手動入力

BookingGateway
  └─ 将来のSHEER予約実行

CalendarGateway
  └─ Google Calendar

RoutePlanner
  └─ 経路検索サービス
```

上記の名称や分割方法は仮案です。実際に採用するか、どの範囲を抽象化するかは未決定です。

## 4. SHEER連携方法の候補

- HTTPリクエストでログインし、Cookieを保持してHTMLを解析する。
- Playwrightなどのブラウザ自動操作を利用する。
- SHEER側に外部から利用できるAPIがあれば利用する。
- 連携を行わず、公式予約ページへ誘導する。

実現可能性を判断するため、ログインフォーム、セッションCookie、HTML、ブラウザ通信、CSRF、CAPTCHA、Bot対策、利用規約などを調査する必要があります。

## 5. 初期の操作フロー候補

予約操作を完全自動化する場合は壊れやすく、誤予約のリスクもあるため、次のような段階導入案が出ています。

```text
空き枠を探す
  ↓
候補を表示する
  ↓
公式予約ページを開く
  ↓
本人が最終確定する
```

予約サイトの状態が想定と異なる場合は、自動操作を停止する案もあります。これは安全方針の候補であり、最終的な操作仕様ではありません。

## 7. 運用上の候補

- 自宅サーバーや常時起動VMは避ける。
- Cloud Runなど、アイドル時に停止できる環境を検討する。
- 無料枠、請求先登録、超過課金、ストレージ費用、通信費を確認する。
- 認証情報、Cookie、OAuthトークン、storageState、自宅住所、APIキーをソースコードやGitに保存しない。
