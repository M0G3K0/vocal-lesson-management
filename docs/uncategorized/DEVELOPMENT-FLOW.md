# 開発フロー

この文書は、開発対象の選定からPull Requestのマージ後の完了処理までの流れと、関連するルールを記録する。

## 開発サイクル

### 作業対象を選ぶ

- 人間は、作業対象のGitHub IssueのURLまたは番号をAIに伝えます。
- AIは、指定されたGitHub Issueを読み取ってから作業内容を整理します。GitHub CLIを使う場合は、URLなら`gh issue view <Issue URL>`、番号なら`gh issue view <番号> --repo M0G3K0/vocal-lesson-management`で取得します。コメントも確認する場合は`--comments`を指定します。
- GitHub CLIの設定ファイルにアクセスできない、認証・権限が不足している、利用可能な読み取り手段がないなどの理由で取得できない場合、内容を推測して進めず、読めないことを伝えて本文の共有を依頼します。

### 作業内容を合意する

- AIは、読み取った項目でやること・作業範囲・完了条件と、それに対する理解度（人間の意図をどれだけ正しく組めているか）を客観的に整理します。
  - 理解度は、Issueのタイトルや本文から推測します。
    - 理解度が50%を切る場合は、人間に意図を質問し、理解度が50%以上になるようにします。
    - 理解度が50%以上の場合は、ほぼ人間の要求を理解しているものとみなし、要求を満たすための提案を考えます。
- AIは、読み取った項目をもとに、人間に提案を行います。
  - 読み取った内容
  - Issueの完了条件を満たすために踏むステップ
- 「Issueの完了条件を満たすために踏むステップ」に、以下が含まれている場合は、その指示に従います。
  1. 「これはなに」と「完了条件」を明確にする
     - このIssueに書くべき「これはなに」と「完了条件」を提案してください。
  2. sub-issueを作成する
     - どのようなsub-issueが必要か、それはなぜかを説明してください。
     - それぞれのsub-issueのタイトル、および「これはなに」と「完了条件」を提案してください。
  3. 必要な方針を決める
     - 完了条件を満たす方針が決まっていない場合は、その方針の候補を、理由も含めて提案してください。
     - 複数案がある場合は、複数提示してください。
       - 松案、竹案、梅案：各案の開発工数が大きく異なる場合に使用します
       - 案A, B, C, ...：開発工数自体は変わらないが、思想が違う場合に使用します
       - 案A, A'：開発工数も思想もほぼ同じで、ちょっとした好みの問題である場合に使用します
     - 複数案を提示したうえで、あなたの推し案を理由をつけて教えてください。よくある理由については、以下の優先順位で判断してください。（なお、以下はあくまで参考例であり、すべてのタスクに対してこれらすべての優先順位を考える必要はありません。また、別の判断軸を利用しても構いません。）
       - プロダクトビジョンとの整合性（プロダクトが目指す姿（ビジョン）と地続きになっているか）
       - 課題解決度（根本的なペインを、最もよく、きれいに解決できる）
       - ユーザー体験（開発者ではなく、エンドユーザーの操作性・直観性・学習コストの低さ）
       - 保守・運用の容易さ（メンテナンス性）
       - パフォーマンスと拡張性（スケーラビリティ）
       - 技術的負債の発生リスク（スピードを優先するあまり、将来的に大規模なリファクタリングが必要になるリスクをどれだけ抱え込むか）
       - 移行・ロールバックの難易度（リリース後に大きな不具合があった際、元の状態に簡単に戻せるか（切り戻し性））
       - 開発工数（ベロシティ。AIを利用して開発するため、上記項目より優先度は低い。ただし、上記項目を検討した結果、まだプロダクトフェーズにそぐわないと判断される場合は、より開発工数の低い案に倒すことも検討する。）
  4. 実装方法を提案する
     - やることや完了条件が明確な場合は、実装方法の具体的な方針を示します。
       - ブランチ名：[ブランチ命名規則](#ブランチ命名規則)をもとに決めます。
       - 実装環境準備：作業ブランチの準備方法、ワークツリーを利用するか否か。
         - 作業中の内容がある場合のみワークツリーを利用します
       - そのブランチで何を行うか。（複数ブランチを立てる場合、それぞれ説明）
- 人間は、AIの提案をもとに、合意するか否かを決めます。人間がNGを出した場合、人間の合意が得られるまで再提案し続けてください。
- GitHub IssueやGitHub Projectsへの書き込みを含む場合、ユーザーの指示に対象と内容が明確に含まれていれば、AIはその指示を許可として扱い、追加確認しません。内容が未確定なら、この段階で関連する操作と最終的な内容・フィールド値をまとめて提示し、一度だけ確認します。そのOKを内容への合意と書き込み許可の両方として扱い、後の段階で同じ操作の許可を再度求めません。

- Issueへの記載やAIとの合意の扱いは、[協働ルール](./COLLABORATION-RULES.md)を参照してください。
- GitHub ProjectsをAIが操作するときのフィールド設定や操作方法は、[GitHub Projects操作ガイド（AI向け）](./GITHUB-PROJECTS-AI-OPERATIONS.md)を参照してください。
- 作業に要求書・仕様書などの文書が必要か、決定事項をいつ文書化するかは、[文書化ルール](./DOCUMENTATION-RULES.md)に沿って判断します。

### 作業環境を準備する

- AIは、すべての項目が合意できたら、合意した内容をもとに作業を始めます。
  - 前段階で承認されたGitHub IssueやGitHub Projectsへの書き込みを、承認された対象と内容の範囲で実行します。ユーザーの指示に対象と内容が明確に含まれていた場合も、その指示の範囲で実行します。承認時と内容や対象が変わった場合は、変更分について改めて確認します。
  - GitHub Projectsのフィールド設定と操作方法は、[GitHub Projects操作ガイド（AI向け）](./GITHUB-PROJECTS-AI-OPERATIONS.md)に従います。
- 実装を含む作業では、作業を始める前にブランチまたはワークツリーを準備します。
  - ユーザーが起点ブランチを明示した場合は、そのブランチを使います。
  - 起点ブランチが指定されておらず、先行作業への依存もない場合は`main`を使います。
  - 後続作業が先行作業の変更に依存する場合は、その変更を含むブランチを起点にします。どのブランチが適切か判断できない場合は、作業前に確認します。
- ブランチの形式は「[ブランチ命名規則](#ブランチ命名規則)」に従います。

### 実装し、確認する

- AIは、合意した範囲に沿って作業します。
- 合意した範囲の実装が終わるまで、基本的に作業は中断してはいけません。
  - ただし、以下の条件をすべて満たした場合、理由を述べたうえで作業を中断してもよいです。
    - 作業途中に特定の原因で行き詰まり、その同一のブロッカーによって10分以上作業が停滞してしまった
    - 作業の行き詰まりを解消する回避策を使うと、人間と合意した内容と成果物がずれる
    - 上記の理由により、人間の要求通りに作業を完遂させることが困難である
  - 逆に、人間との合意条件を満たしつつ、別の回避策で作業を進行させることができるのであれば、作業中断前にその回避策を試してください。
- 実装終了後、以下を整理します。これは人間に報告する用です。
  - なぜ・どのような変更を行ったか
  - テストで確認したことは何か
  - 人間にレビューしてほしい項目（以下の形式を守ること）
    - 項目番号（1から順に連番で）
    - AIによる自己確認の結果（OK, NG, 未確認）
    - 種類（WEB、APIなど）
    - 場所（対象画面の該当箇所、APIエンドポイントなど）
    - 条件（そのテスト項目を成り立たせる条件）
    - 手順
    - 期待する動作
    - 備考（あれば）
  - ※人間は、この項目番号順にOKまたはNGを検査します。この項目に必要なテストが含まれていない場合、本番でバグが発生する可能性があります。そのため、人間にレビューしてほしい項目を網羅的に記述してください。
    - 正常系
    - 異常系
    - 今回の変更で影響する可能性がある箇所のデグレチェック

### ローカルで動作確認を行う

- AIは、作業が終了したら、作業した内容を人間に報告します。
  - なぜ・どのような変更を行ったか
  - テストで確認したことは何か
  - 人間にレビューしてほしい項目
- 人間は、作業内容を確認し、テストします。
- 人間は、テスト項目番号に沿って、OKかNGかをAIに申告します。
- AIは、すべての項目がOKになったら次に進みます。

### Pull Requestを準備し、レビューに対応する

- 人間がすべての動作確認項目をOKにした後、AIはコミット案を提示します。コミットごとに、順序・含める変更・コミットメッセージ案を示します。コミットは1つでも複数でもよく、メッセージの形式は固定しません。
- 人間がコミット案にGOを出した後、AIは承認された内容でコミットします。コミット案から変更が必要になった場合は、変更内容を示して改めて確認します。
- コミット後、AIは`git status`を確認し、作業ツリーの状態と今回の変更が分かるように報告します。
- AIはPull Requestのタイトルと本文の案を提示します。タイトルは「[Pull Requestタイトル命名規則](#pull-requestタイトル命名規則)」、本文は「[Pull Requestテンプレートの利用](#pull-requestテンプレートの利用)」に従います。
- ユーザーがタイトルと本文を確認した後、pushとPull Requestの作成はユーザーが行います。
- 人間は、PRにレビューがある場合、それをAIにお願いします。
- AIは、レビュー内容を客観的に精査し、そのレビューの対応を行う必要があるか・その理由や意図を人間に伝えます。
  - その後、対応する必要がある場合は、実装時と同じように手順を踏んで実装します。
  - その後、作業した内容を、同様に人間に報告します（追加対応した分のみでOK。人間の確認項目も、追加対応によってデグレする可能性がある場合にのみ行います）
- 人間は、すべてOKと判断できたら、マージします。

### 作業を完了する

- 人間は、マージ後に対象IssueがCloseされたことを確認します。
- Pull Request本文に`Closes #<Issue番号>`を記載した場合は、GitHubの標準機能によって対象IssueがCloseされます。
- Closeされていない場合は、Pull Requestのマージ先と本文のIssue番号を確認したうえで、必要ならIssueを手動でCloseします。


## ブランチ命名規則

`main`以外のリモート作業ブランチは、次の形式にする。

```text
<種別>/VLM-<Issue番号>-<短い説明>
```

この形式は、ブランチ名から対象のGitHub Issue、作業の種別、作業内容を把握しやすくするために使う。対象はpush先のリモートブランチ名であり、ローカルブランチ名とは異なる名前でpushする場合も、リモート側の名前をこの形式にする。`main`はIssueごとの作業ブランチではないため、この規則の対象外とする。

種別には、作業の主目的に応じて次のいずれかを使う。

- `feat`: 利用者から見える機能の追加・拡張
- `fix`: 不具合の修正
- `refactor`: 利用者から見える動作を変えない内部構造の変更
- `test`: テストの追加・変更が主目的の作業
- `docs`: 文書だけを変更する作業
- `chore`: リポジトリ設定、ツール、依存関係、CI、開発環境などの整備

短い説明は、作業の動詞と対象が分かる表現にする。対象は新機能や作成物に限らず、修正する動作、調査対象、検証対象、文書などを含む。一般に通じる略語は使ってよい。長さの固定基準は設けない。

複数の変更を含む場合は、ブランチの主目的に合う種別を選ぶ。例えば、機能に伴うテスト追加は`feat`、不具合修正に伴う回帰テスト追加は`fix`とする。テストだけを追加・変更する作業では`test`を使う。

例：

- `feat/VLM-41-add-reservation-search`：予約検索機能を追加する
- `fix/VLM-42-handle-empty-reservation-list`：予約一覧が空の場合の動作を修正する
- `refactor/VLM-43-extract-calendar-client`：Calendar連携処理を切り出す
- `test/VLM-44-verify-route-calculation`：経路計算のテストを追加する
- `docs/VLM-45-document-branch-naming`：ブランチ命名規則を文書化する
- `chore/VLM-46-update-gradle-wrapper`：Gradle Wrapperを更新する

### Push前の形式確認

`.githooks/pre-push`は、push先のリモートブランチ名について、種別、`VLM-`に続く0より大きい数字のIssue番号、区切り、および空でない短い説明を機械的に確認する。Issue番号が実在するか、短い説明が動詞と対象を表しているかなど、説明の内容の妥当性は自動判定しない。

ブランチ名は作業内容を後から把握しやすくするための規約であり、名前が規則に合うことは変更内容の正しさを保証しない。規則違反でもマージできてよいものとし、命名違反を理由に作業を止めると開発が遅れる可能性があるため、形式確認は英語の警告にとどめる。警告の出力に失敗した場合もpushは中断しない。警告が表示するルールの詳細は、この文書を正とする。

このリポジトリでフックを有効にするには、次を一度実行する。

```sh
git config --local core.hooksPath .githooks
```

フックの振る舞いを確認するには、リポジトリのルートで次を実行する。

```sh
sh tests/pre-push-hook-test.sh
```

## Pull Requestタイトル命名規則

Pull Requestタイトルは、通常、対象のGitHub Issueタイトルに合わせ、次の形式にする。

```text
VLM-<Issue番号> <GitHub Issueのタイトル>
```

同じGitHub Issueに対する修正など、Issueタイトルと異なる変更内容を示したい場合も、この形式を使う。例えば、Issue 31に対する修正Pull Requestなら次のようにする。

```text
VLM-31 【fix】CI検査の説明を修正
```

CIは、タイトルが`VLM-<数字> <空でない説明>`の形式かを検査する。Issue番号が実在するか、説明がGitHub Issueタイトルと一致するかは検査しない。形式に合わない場合はCIを失敗させる。`main`へのマージを止めるには、GitHubのルールセット`main-pr-required`でこのチェックを必須にする。

このCIチェックの名前は`PR title validation`とする。

Pull RequestをSquash mergeしたときのコミットタイトルには、コミット数にかかわらずPull Requestタイトルを使う。

## Pull Requestテンプレートの利用

Pull Request本文は、`.github/pull_request_template.md`の項目に沿って作成する。テンプレートは`main`に含まれると、GitHub上で新しくPull Requestを作成するときに本文へ表示される。GitHub CLIで作成する場合は、次のようにテンプレートを指定する。

```sh
gh pr create --template .github/pull_request_template.md
```

AIがPull Request本文を作成するときも、このファイルを読み、各項目に沿って内容を記載する。

Pull Requestをマージした後に対象IssueをCloseすることが基本であるため、Pull Request本文には原則として`Closes #<Issue番号>`を記載する。マージ後も対象IssueをCloseしない場合だけ、この記載を省略する。
