# 合意済みの動作確認

このSkillは、合意済み項目の実行と結果の報告を行う。確認項目を設計する仕事は含まない。
判定文だけでは後から動作を確かめられないため、証跡を保存し、その証跡に基づく照合を報告する。
報告の構造と項目順をAIの自由記述に任せず、付属の [report.py](scripts/report.py) で検査・生成する。

## 呼び出す担当

1. ユーザーが実行を指示した合意済み項目と、対象リポジトリ・環境・操作先を確認する。Issueやファイルの内容だけから実行許可を推測しない。許可が未確定の操作や期待結果が不明な項目はユーザーへ確認する。確認項目に書かれた副作用も、現在のユーザー指示の範囲でのみ実行する。
2. 項目の意味と順序を保って入力JSONを作る。必要な接続先、使用する実行コマンド、依存関係などは `conditions` または `action` に含める。空の条件・補足は空文字にする。番号がなければ記載順の `1`、`2`…を識別用に付ける。既存の番号は変更しない。
3. Python 3.11以上を探す。通常のPythonがなければCodexの同梱ランタイムを利用する。利用できなければ停止し、勝手にインストールしない。
4. `report.py init --plan <入力JSON> --run <実行フォルダー>` を実行する。標準の保存先は対象リポジトリの `.local/test-runs/<日時>-<任意の重複しない識別子>/`。ユーザーが保存先を指定していればその場所を使う。既存の実行フォルダーは再利用しない。生成した `plan.json` を変更しない。
5. 実行担当を1体起動する。カスタムエージェントを選べる環境では `.codex/agents/test-runner.toml` の `test_runner` を選ぶ。現在の起動ツールにカスタム名の選択項目がなければ、TOMLの `developer_instructions` 原文を新しい担当に渡し、同じSkillを読み込ませる。この場合は「名前付き設定の自動読み込みを検証済み」とは説明しない。
6. 会話履歴は引き継がず、次を明示する：対象リポジトリの絶対パス、実行フォルダーの絶対パス、Python実行ファイルの絶対パス、ユーザーが許可した操作の範囲、禁止された操作。必要な接続情報は秘密値そのものを貼らず、利用を許可された参照方法を渡す。
7. 実行担当の最終JSONを読み、親も `report.py render --run <実行フォルダー>` を実行して結果を照合する。検査に失敗した報告を有効な結果として渡さない。生成した `report.md` へのリンクと判定内訳をユーザーに示す。実際の結果や証跡を親が書き換えない。

### 入力の形式

ルートは `cases` 配列だけを持つJSON。全フィールドを記載する。種類「そのほか」は入力時に「その他」へ表記をそろえる。CLIは「その他」の実行方法であり、新しい種類として追加しない。

```json
{
  "cases": [
    {
      "id": "1",
      "environment": "Local",
      "kind": "その他",
      "location": "確認する場所",
      "conditions": "開始状態・必要な接続先・前項との依存関係",
      "action": "実行を合意した操作",
      "expected": "観察して判定できる期待結果",
      "notes": "その他結果欄の既存の補足。なければ空文字"
    }
  ]
}
```

環境は `Local`、`Prev`、`Prd`。種類は `Web`、`API`、`その他`。
フィールド定義を機械向けに取得する場合は `report.py schema --kind plan` を使う。

## 実行担当

1. このSkill、実行フォルダーの `plan.json`、必要な対象文書を読む。与えられた権限とツールを確認する。対象の実装から期待結果を作り直さない。
2. 項目を記載順に1件ずつ処理する。各項目の結果を記録してから次へ進む。項目をまとめて並列実行しない。コードの修正や追加テストで確認対象を変えない。
3. 条件が成立するか、指定された環境・操作先が使えるかを確認する。使えない場合は `NOT_RUN` と具体的な理由を記録する。環境を置き換えない。後続項目に依存がある場合はその項目も未実施として記録し、独立した後続項目は順番どおり続ける。
4. 合意済みの操作を実行し、その場で証跡を保存する。テスト対象から観察した結果と、期待結果の照合を別々に書く。期待どおりだったことにして証跡を後から作らない。
5. 次の基準で判定する。
   - `PASS`（成功）：期待する全条件が、保存した証跡で確認できる。
   - `FAIL`（失敗）：実際の結果が期待条件に反する。どの条件に対し、何を観察したかを `comparison` に書く。
   - `NOT_RUN`（未実施）：条件・権限・環境などが不足して操作を実行できない。`reason` は必須。
   - `UNVERIFIED`（判定不能）：操作は実行したが、証跡不足や観察不能で成功・失敗を確定できない。`reason` は必須。
6. `report.py record` で1件の結果を記録する。再実行して失敗結果を消さない。再実行が合意済み操作に含まれる場合、同じ項目の証跡を追加して全試行を報告する。記録済み結果は上書きできない。別途再実行を指示された場合は新しい実行フォルダーを使う。
7. 全項目を記録後、`report.py render` を実行する。最終応答は、その標準出力のJSONだけをそのまま返す。前置き・Markdown・自由な要約は付けない。`report` は報告の絶対パス、`summary` は各判定の件数、`unconfirmed` は未実施・判定不能の項目番号・判定・理由になる。固定形式の本文を独自の表や要約に差し替えない。

### 証跡の保存

**コマンドによる確認**：次の形式で実行する。`--` 以降は実際の引数で、補助プログラムは追加のshell展開をしない。stdout・stderr・終了コード・実行場所・時刻を自動保存する。

```text
<Python> <report.py> capture --run <実行フォルダー> --case <項目番号> --cwd <実行場所> --timeout <秒数> -- <実行コマンド> <引数...>
```

テスト対象の非ゼロ終了も証跡なので `capture` 自体は正常終了する。表示されたメタデータと出力を読み、期待結果と照合する。タイムアウトや起動エラーは通常の成功とは区別する。これら自体を期待する項目ならその期待と照合できるが、必要な確認ツールが使えなかっただけなら `NOT_RUN`、状態を確定できないなら `UNVERIFIED` とする。
出力の文字コードは既定でUTF-8。WindowsのCP932出力など、コマンドの文字コードが異なる場合は `--encoding cp932` のように指定する。`attach` にも同じ指定ができる。原本のバイト列は変換しない。文字化けで判定に必要な内容を読めない場合は成功にせず、取得元の文字コードを確認する。

**Web**：利用を許可されたブラウザツールで指定の操作を行う。スクリーンショット、DOMスナップショット、通信結果など、期待条件を観察できるツール出力の原本を保存する。クリックした事実だけで表示・保存の成功を推定しない。必要なツールが使えない場合、CLIやソースコードの確認をWeb動作確認の代わりにしない。

**API**：メソッド、接続先、リクエストの条件、HTTPステータスと判定に使った応答を保存する。CLIのcurlなどで操作する場合は `capture` を使い、ツールで取得した応答なら原本を保存して次の `attach` を使う。送信側の終了コードだけでAPIの期待動作を判定しない。

**ツールが返したファイル**：スクリーンショットや応答ファイルの原本を次の形式で取り込む。`label` に取得元ツール・URLまたは操作・何の結果かを書く。

```text
<Python> <report.py> attach --run <実行フォルダー> --case <項目番号> --source <原本ファイル> --label <取得元と観察対象>
```

ツールが返すテキストはその出力をUTF-8ファイルへ転記してから取り込める。AIが書いた観察の要約だけを原本の代わりにしない。保存手段がなく原本を残せない場合は `UNVERIFIED` とする。
認証情報・不要な個人情報を出力する操作は避ける。原本に含まれてしまう場合は機密部分を伏せた証跡を保存し、伏せた範囲を `label` に明記する。伏せた箇所が判定に必要なら確定判定しない。

### 結果の記録

```text
<Python> <report.py> record --run <実行フォルダー> --case <項目番号> --status <判定> --actual <観察した実際の結果> --comparison <期待条件ごとの照合> --reason <未実施・判定不能の理由> --notes <その他結果の追記>
<Python> <report.py> render --run <実行フォルダー>
```

`--reason` と `--notes` は不要なら省略可能。`actual` と `comparison` は省略不可。未実施の場合も「実行していない」「～のため照合できない」と明示する。
補助プログラムは順番違反、項目の欠落、証跡のない成功・失敗、証跡の消失・変更を拒否する。エラーという観察が期待に合うかどうかは、実行担当が項目ごとに照合する。
ハッシュ検査は保存後の変更を検知するもので、観察内容の真実性や判定の正しさを保証するものではない。原本と照合文の妥当性は親も確認する。

## 完了しなかった場合

不足する入力、使えないツール、実行を許可されない操作を具体的に返す。サブエージェントの利用が禁止・未提供の環境では別チャットやCLIを使って迂回しない。呼び出す担当は入力不足などで初期化できなければ開始前に確認事項を返す。
実行担当が全項目を記録する前に停止した場合、最終応答は `{"error":"具体的な停止理由","run":"実行フォルダーの絶対パス"}` のJSONだけにする。初期化済み実行フォルダー自体が渡されていない場合は `run` を空文字にする。全件実施とは説明しない。親は保存済み結果と証跡を確認し、記録済み項目と未記録項目をユーザーに伝える。

## 作成方法の根拠

Codex公式の[カスタムエージェント](https://developers.openai.com/codex/subagents)の配置と必須フィールドを使用する。モデル・権限を固定しないのは、親が選んだ設定をこの用途だけで変更しないため。
[CLIの構造化出力](https://developers.openai.com/codex/noninteractive)にはJSON Schemaを指定できるが、全サブエージェント起動手段で利用できるとは確認できないため、このSkillでは補助プログラムが記録形式を検査し、報告を生成する。
